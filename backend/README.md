## Seed data
`python manage.py load_seed [--data-dir PATH] [--demo-users]` loads `data/seed/` (tenants, suppliers,
purchase orders + lines, inventory, shipments) in one transaction. It is idempotent: run it again and
it reports 0 created / 0 updated. In Docker the compose file mounts `./data` read-only at `/data`, so the default seed folder resolves; run `docker compose exec backend python manage.py load_seed`. Any validation failure aborts everything with a `CommandError`
naming the file, the record id and the rule.
- `--data-dir PATH` loads another seed folder (e.g. one made with `data/generate_seed.py --as-of ... --out ...`);
  records are updated in place. Default comes from `SEED_DATA_DIR` (settings), else `<repo>/data/seed`.
- `--demo-users` also creates `<tenant>.admin`, `<tenant>.procurement`, `<tenant>.viewer` per tenant
  (e.g. `acme.admin`). The password comes only from the env var `DEMO_USER_PASSWORD` (must pass Django
  password validation, is never printed, existing users keep their password). Without the flag no users are created.

## Correlation id and audit
- `CorrelationIdMiddleware` (first in `MIDDLEWARE`) reads `X-Correlation-ID`; a valid UUID is kept (lowercased), anything else is replaced by a new v4. The id is on `request.correlation_id`, in a ContextVar (`apps.audit.context.get_correlation_id()`), in every log line (`[%(correlation_id)s]`) and on every response, errors included.
- `from apps.audit import record`; `record(actor, action, entity=None, correlation_id=None, data=None, tenant=None)` appends an `AuditEvent`. `actor` is a `User` (stored as `USR-<n>`), `'SYSTEM'` or a string; `entity` is a model instance or a `(type, id)` tuple; tenant defaults to the entity's, then the actor's; the correlation id defaults to the current request's. `data` must be JSON-safe; keys such as password/token/secret/api_key/authorization/cookie are stored as `[REDACTED]`.
- `GET /api/v1/audit?entity_type=&action=&correlation_id=&from=&to=` is read-only and scoped to the authenticated user's tenant (never taken from the query).
- `apps.core.handlers` gives `/api/` paths the JSON 400/403/404/500 error body. With `DEBUG=True` Django's own technical 404/500 pages win, so the frontend sees HTML there in development.
- Redaction is by key name (separators ignored: `X-Api-Key`, `api_key` and `apiKey` all match password/secret/token/authorization/cookie/credential/apikey/privatekey/jwt/bearer/signature/session, plus the exact keys access/refresh/key) and by values starting with `Bearer ` or `Basic `. Numbers, booleans and null stay visible (`prompt_tokens: 12`). Callers must never put raw credentials in values under other keys.
- `record()` raises `ValueError` when the explicit tenant, the entity's tenant and the actor's tenant disagree, or when a field exceeds its column length.
- Log lines carry the id, including Django's 4xx/5xx `django.request` lines (taken from the request, since they are logged after the middleware ends). The dev server's own access lines (`django.server`) cannot carry it; gunicorn access logs get it from the response header in U-12.

## Authentication
- `POST /api/v1/auth/token` `{username, password}` -> `{access, refresh}`. Access-token claims: `user_id`, `tenant_id`, `role`. Inactive users, users without a tenant (superusers included) and users of a non-ACTIVE tenant get the same generic 401 as a wrong password.
- `POST /api/v1/auth/refresh` `{refresh}` -> `{access}` (no rotation, no blacklist). The user, tenant and role are re-read from the database, so a role change shows in the next access token and a deactivated user cannot refresh.
- The database is the source of truth: `TenantJWTAuthentication` returns 401 when the token's `tenant_id`/`role` differ from the user's current values. `request.tenant` is set only from the credential (user's tenant or the API key's tenant); use `getattr(request, "tenant", None)`.
- `GET /api/v1/me` -> `{id, email, name, role, tenant: {id, name}}` for real users of an active tenant (403 for SYSTEM and tenant-less superusers).
- SYSTEM callers (Boomi): `python manage.py create_api_key --tenant TEN-ACME --label boomi` prints the key ONCE (`sgk_` + 40 chars); only its sha256 hash and 8-char prefix are stored. Send it as `X-Api-Key`. Rejected keys write `security.api_key_rejected` audit rows (prefix only). Disable a key with `is_active` in the admin.

- Throttling and failed credentials (per client IP per minute unless stated). The counters (throttles and `apps/accounts/failguard.py`) live in each process's local cache, so every gunicorn worker counts separately and the effective limit is rate x workers: use a shared cache (Redis) in production.
  - `/auth/token`: `AUTH_THROTTLE_RATE` (default `10/min`) limits requests per IP. In addition `AUTH_USERNAME_THROTTLE_RATE` (default `10/min`) limits FAILED logins per (lowercased) username; successful logins never count. Once a username has that many failures in the minute, every login for it, including one with the CORRECT password, gets 429 until the minute is over. Trade-off: anyone who knows a username can lock that account out of logging in for the rest of the minute by sending bad attempts; the alternative (no per-username limit) lets an attacker rotate IPs without limit.
  - `/auth/refresh` has its own budget, `AUTH_REFRESH_THROTTLE_RATE` (default `60/min`), so refreshing never uses up logins.
  - `NUM_PROXIES` (default `0`): number of trusted reverse proxies in front of Django. Set it to `1` behind the U-12 proxy. With `0` the `X-Forwarded-For` header is ignored, so a spoofed header cannot create new throttle buckets; if it is too low behind a proxy every client looks like the proxy, if it is too high a client can spoof its address.
  - Failed API keys and logins: at most `AUTH_FAIL_AUDIT_PER_MIN` (default `10`) audit rows per IP per minute for EACH kind (`security.api_key_rejected`, `auth.login_failed`; one warning with the IP and the skip count is logged when writes start being skipped). After `AUTH_FAIL_LIMIT_PER_MIN` (default `30`) failed API keys from one IP in a minute, a further request with a WRONG key gets `429` (`RATE_LIMITED`) instead of 401. A valid, active key on an ACTIVE tenant always authenticates, from any IP: the key is looked up first and only failed attempts are counted, because egress IPs (Boomi Atom Cloud) are shared by tenants.
  - `auth.login_failed` rows keep `data.username` only when it matches an existing user (case-insensitive); otherwise `{"username_known": false}`, because people paste passwords into the username box.
- Refresh tokens are not rotated or blacklisted. To revoke a stolen refresh token, deactivate the user (or the tenant): `/auth/refresh` re-reads the user and the tenant from the database.
- `/api/schema/` and `/api/docs/` are public for now; gate them with `SPECTACULAR_SETTINGS["SERVE_PERMISSIONS"]` in U-12.

## Roles and tenant scoping
How to add an endpoint (other streams: read this first).
- **Permissions.** `DEFAULT_PERMISSION_CLASSES` is `RolePermission`, so a view without a `permission_key` is refused (403). One place decides who may call what: `ROLE_MATRIX` in `apps/accounts/permissions.py` (permission key -> HTTP method -> allowed roles; `routed=False` rows are declared for endpoints that are not built yet). On your view set `permission_key = "suppliers.read"` (or `{"GET": "users.read", "POST": "users.write"}` when one URL needs different keys per method). Public views must set `permission_classes = [AllowAny]` explicitly. An unknown key, or a method the matrix does not list for a method the view implements, is refused; no credential is 401.
- **Routing a declared row.** When you build the endpoint of an existing row: flip it to `routed=True` in `ROLE_MATRIX`, add its URL to `ROUTES` and its key to `EXPECTED_ROUTED` in `tests/test_role_matrix.py`. `EXPECTED` there is the hand-written table copied from `docs/CONTRACTS.md` s2/s4: any change to a role list must be made in both places on purpose. The matrix tests then check every role (4 JWT users plus a SYSTEM API key) against every routed method, and that every view key is in the matrix.
- **Who passes.** The principal needs an ACTIVE tenant (tenant-less superusers and users of an INACTIVE tenant: 403 "No active tenant for this credential."). SYSTEM (API key) passes only where the matrix lists it. A role that is not listed gets 403 ("Your role is not permitted for this endpoint." / "This credential is not permitted for this endpoint.").
- **Current rows:** `me.read` (all 4 user roles), `settings.*` and `users.*` (ADMIN), `audit.read` (ADMIN + PROCUREMENT_MANAGER: the agenda D-2.6 suggestion, NOT yet approved).
- **Tenant scoping.** Use `apps.core.tenancy.TenantScopedMixin` (or `TenantScopedViewSet`) for every tenant-owned model. Your `queryset` must start from `super().get_queryset()` if you override `get_queryset()` (that is where the tenant filter lives); set `lookup_field = "erp_id"` for ERP-keyed models (the lookup is then tenant + erp_id, never the bare id). The tenant is `request.tenant`, set from the JWT user or the API key; `tenant`/`tenant_id` in the body or query are never read. Without an ACTIVE tenant the view answers 403. Another tenant's id answers the same 404 as a missing id and writes a `security.cross_tenant_denied` audit row under the requester's tenant (TC-10); a row of your own tenant that your narrowed queryset hides is a plain 404 without that row. `perform_create` stores the row in the requester's tenant.
- **Audit.** `from apps.audit import record`; `record(actor, action, entity, data=...)` where `actor` is a `User`, a `SystemPrincipal` (what `request.user` is for an API-key caller: stored as actor `SYSTEM` with the key's tenant; an explicit different `tenant=` raises `ValueError`) or a string such as `"SYSTEM"`. If you pass the plain string `"SYSTEM"` you must also pass `tenant=request.tenant`, or the row is written with no tenant and is invisible to the tenant. Never read the tenant from anywhere but `request.tenant`.
- **Views.** Use class-based DRF views only: `@api_view` function views cannot declare a `permission_key` and are always refused (403); do not reach for `IsAuthenticated`. All `@action` routes of one ViewSet share the view's `permission_key`, so give a per-HTTP-method mapping (`{"GET": ..., "POST": ...}`) or split them into separate views. `tests/test_review_round2.py` fails if a DRF view under the project urlconf neither uses `RolePermission` nor is on its explicit public list (login, refresh, schema, docs).
- **Production check.** `manage.py check` warns (`accounts.W001`) when `DEBUG` is off and `NUM_PROXIES` is not set in the environment: set it to the number of trusted proxies (1 behind the U-12 proxy).
- `GET/PATCH /api/v1/settings` (ADMIN): the tenant's effective settings. `risk_thresholds.exposure_full_scale` is optional (number in (0, 1e12]); when it is not stored the response shows `500000` (the default the impact engine uses) and the database keeps the stored value. Thresholds are 0..100 with `medium < high < critical`, `max_cost_increase_pct` is 0..1000. PATCH is partial, validated by `apps.tenants.settings_schema.validate_tenant_settings`, runs under a row lock and writes `settings.updated`. Unknown keys (including `tenant`/`tenant_id`) are a 400.
- `GET/POST /api/v1/users` (ADMIN, own tenant): roles ADMIN / PROCUREMENT_MANAGER / OPS_MANAGER / VIEWER only; the password is write-only, checked with Django's password validators and never audited; `is_staff`/`is_superuser` cannot be set. Usernames are NFKC-normalised, limited to letters, digits and `. @ + - _`, and unique case-insensitively. Accepted trade-off: because usernames are unique across all tenants, an ADMIN can learn that a username is taken in another tenant (the error is the same generic 400 and shows nothing else). No update or delete routes yet.

## Event intake and the Boomi client (U-06)
- `POST /api/v1/events/disruptions` (API key or ADMIN): validates the canonical event, then in this order: tenant check (a payload `tenant_id` different from the credential's tenant is a 403 + `security.tenant_mismatch` audit row, before any write; the tenant is never taken from the payload), dedupe on `(tenant, event_id)` (duplicate = 200 with the stored `correlation_id` and `risk_case_id`, no Boomi call), create + audit in one transaction (a lost insert race is answered as a duplicate), then publish to Boomi AFTER the commit. New event = 202 `{event_id, correlation_id, status: "RECEIVED", risk_case_id: null}`. An unknown or other-tenant supplier gives the identical 202 but the event is stored with `needs_data_correction=true`, nothing is sent to Boomi and no RiskCase exists (only the audit row `event.flagged_data_correction` differs). A Boomi failure keeps the event (`publish_status=PUBLISH_FAILED`, audit `event.publish_failed`) and still answers 202; an empty `BOOMI_BASE_URL` leaves `RECEIVED` and audits `event.publish_skipped`.
- Event intake details: `event_time` must be in the years 2000-2100; a DUPLICATE of an event whose publish never succeeded (`RECEIVED` with a known supplier, or `PUBLISH_FAILED`) is published again (the Idempotency-Key makes that safe) and still answers 200 with the same body; a duplicate of a `PUBLISHED` event or of an unknown-supplier event never calls Boomi. Intake is throttled per credential (API key id / user id, not IP): `EVENTS_THROTTLE_RATE` (default 300/min) and `SIMULATE_THROTTLE_RATE` (default 10/min) -> 429 `RATE_LIMITED`; duplicates are audited (`event.duplicate`) so the throttle caps them. Counters are per worker (local-memory cache). A JSON body nested absurdly deep is a 400 on every endpoint (`apps.core.parsers.SafeJSONParser`). `EVT-9xxxxx` ids are reserved for simulation (the sequence is recreated at 900000 if missing and ids the tenant already has are skipped).
- `POST /api/v1/demo/simulate-disruption` (ADMIN): body `{scenario, event_time?, fresh_event_id?: true}`; `scenario` is a file stem in `SCENARIO_DIR` (`^[a-z0-9_]+$`), always sent for the caller's tenant through the same `intake_event` function; fresh ids come from the `EVT` sequence (EVT-900001, ...), `fresh_event_id=false` keeps the scenario's id so a repeat is a duplicate; the scenario's `send_times` is honoured.
- `GET /api/v1/integrations/status` (ADMIN): Boomi `configured / auth_mode / host / reachable / latency_ms / checked_at` (probe cached 10 s, hostname only, never keys) and tenant-scoped `events_24h` counts.
- `apps/integrations/boomi.py`: `BoomiClient` (httpx). Retries ONLY timeouts, connection errors and HTTP 429/502/503/504 (`BOOMI_MAX_RETRIES`, exponential `BOOMI_BACKOFF_SECONDS`); other 4xx are never retried. `BoomiError.kind` = VALIDATION / AUTH / BUSINESS / TRANSIENT / DOWNSTREAM (like `Execution.error_class`). The key, the Authorization header and bodies are never logged or put in errors/audit rows. Tests override `apps.integrations.boomi.get_boomi_client` (see `tests/boomi_helpers.py`, an `httpx.MockTransport` recorder).
- Settings (see `.env.example`): `BOOMI_BASE_URL` (empty = not configured), `BOOMI_API_KEY`, `BOOMI_AUTH_MODE` (`apikey` header `X-Api-Key`, or `basic` with `user:password`), `BOOMI_EVENT_PATH` (default `/ws/simple/createDisruptionEvent` is a PLACEHOLDER until U-08/U-09 define the real route), timeouts, retries, `SCENARIO_DIR` (default `<repo>/data/scenarios`; `/data/scenarios` in Docker).
- Publish budget: the publish runs INSIDE the intake request, so it is bounded. `BOOMI_TOTAL_TIMEOUT_SECONDS` (default 8) covers ALL attempts and backoffs (each attempt's timeouts are capped to the time left; no retry starts when the budget is gone); defaults `BOOMI_TIMEOUT_READ=5`, `BOOMI_MAX_RETRIES=1`; the failure is `TRANSIENT` with the attempts counted. `BOOMI_BASE_URL` / `BOOMI_EVENT_PATH` with credentials (`user:pass@`), a query string or a fragment are refused at start (`NOT_CONFIGURED`); the `httpx`/`httpcore` loggers are at WARNING because they log full URLs at INFO. For production the right design is an outbox + a background publisher with a sweeper (U-11) instead of a synchronous call.

- `POST /api/v1/internal/risk-cases` (API key only; ADMIN/PM/OPS/VIEWER get 403): Boomi's callback with `{event_id, snapshot: {captured_at (aware ISO), supplier (object|null), purchase_orders[], inventory[], alternate_suppliers[], shipments[]?, supplier_history[]?}}` (same field names as the ERP responses, plain lists, max 5000 rows per list, unknown keys 400, duplicate `po_id` 400, body size limited by `DATA_UPLOAD_MAX_MEMORY_SIZE`). `apps/integrations/risk_cases.py` is the wrapper; the creation is N-04's `apps.intelligence.services.create_risk_case` (engine + RiskCase + AffectedPO). Wrapper duties, in order: tenant-scoped event lookup (another tenant's event = the same 404 as an unknown one + audit `security.cross_tenant_denied` in the caller's tenant); then in ONE transaction with the event row locked: flagged event = 409; existing case = 200 with it (a case still in RECEIVED is moved to ANALYZING); `supplier` null = event flagged, `200 {risk_case_id: null, flagged: true}`; range checks (`snapshot_checks.py`: amounts < 10**12, ids <= 40 chars, item_name <= 200, currency `^[A-Z]{3}$`, quantities < 10**9) and a tenant check of shipments/supplier_history rows (N-04 does not check those), then `create_risk_case` (N-04 requires `tenant_id` on every supplier/PO/inventory/alternate row and the snapshot supplier to be the event's supplier); no affected PO line = `200 {risk_case_id: null, no_impact: true}` (no case, event NOT flagged); otherwise RECEIVED -> ANALYZING via `apps.workflow.services.transition()` (trigger SYS_IMPACT, actor SYSTEM) and audit `risk_case.created` (counts only, never the snapshot). Any bad or out-of-range value is a 400 with a message that names the field, never the value (also `DataError` / `InvalidOperation` / `OverflowError` on the write); nothing is kept. Response `201` (or `200` for an existing case) `{risk_case_id, status (ANALYZING), risk_level, risk_score, exposure: {amount, currency}, affected_po_count, data_quality_flags, correlation_id}`.
- `POST /api/v1/internal/executions/<id>/result` (API key only): body `{status: SUCCEEDED|FAILED, attempt (int >= 1, the `ExecutionRequest.attempt` Boomi echoes), verified?, response_status?, response_payload?, error?, error_class?}`. Validation and sanitising happen here: FAILED needs `error_class` + `error`; a SUCCEEDED without `verified: true` is NOT a 400 (that would leave the execution RUNNING): it is recorded as FAILED / BUSINESS `ERP change not verified` (not retryable), as N-10 prescribes; `response_payload` and `error` are redacted (audit redaction rules) and the payload is capped at 20 KB (truncated with a `_truncated` marker, never rejected). The execution is looked up in the credential's tenant (foreign = missing = the same 404, foreign also audited), then `apps.workflow.services.record_execution_result` updates the Execution and moves the case (SUCCEEDED -> RECOVERED, FAILED -> EXECUTION_FAILED) in one transaction: a stale `attempt` is 409 `STALE_EXECUTION_RESULT`, a non-running execution 409 `EXECUTION_NOT_RUNNING` (also a different second terminal result), the identical result again 200 without change. Response `{execution_id, status, error_class, finished_at, case_status, retryable}`. Code: `apps/integrations/executions.py`. The `ExecutionTrigger` (`WORKFLOW_EXECUTION_TRIGGER`, what actually starts the Boomi execution) is U-10's job and is not implemented here.

### Migration `accounts.0004` and case-duplicate usernames
`0004_user_username_lower_unique` adds a database-level unique rule on `lower(username)`. It fails on a database that already holds two usernames differing only by case (the API cannot create those, but `createsuperuser` or an ad-hoc script could have). If a shared dev database hits this, rename the duplicates first (for example `UPDATE accounts_user SET username = username || '_2' WHERE id = <id>`), then migrate. A fresh database or the `load_seed --demo-users` accounts are not affected.
